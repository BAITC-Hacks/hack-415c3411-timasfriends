# Задание серверному AI-агенту: QuestBridge

Ты реализуешь сервер для пятичасового хакатона. Клиент делает другой разработчик в Unity 6000.3.7f1, целевая платформа — WebGL. Создай сервер в `backend/`, не изменяй Unity Assets/Packages/ProjectSettings. Используй FastAPI, Pydantic и SQLite. Нужен работающий MVP с простой инструкцией запуска, воспроизводимыми примерами и API ниже. Не ограничивайся планом. Не публикуй и не пушь изменения без согласования с владельцем репозитория.

## Продукт

Бизнес пишет первоначальное описание проблемы. AI задаёт три уместных уточняющих вопроса по очереди: один вопрос, отдельный ответ пользователя, сохранение данных, следующий вопрос. После третьего ответа формируется редактируемая карточка задачи. Человек проверяет и подтверждает её перед публикацией. Сервер начисляет баллы готовности по прозрачной формуле. Подтверждённая карточка попадает в общий каталог: сначала сортировка по готовности, при равенстве — по дополнительной оценке ясности AI. Студенческие команды подают идею, план, срок и ссылку на прототип. Бизнес сам выбирает одну, несколько или ни одной команды. За подтверждённый этап выбранная команда получает баллы опыта.

В Unity одно окно: слева AI-чат, в центре каталог с анимацией изменения позиций, справа сведения о выбранной команде. Возле карточки — аватары команд, подавших отклики. Unity получает JSON, сама рисует интерфейс. Не возвращай HTML, Markdown-разметку экранов или сгенерированные изображения.

## Границы

- Не нужны полноценная регистрация, студенческая база, платежи, аукцион, чат между людьми, уведомления, векторная БД и обучение модели.
- Используй демонстрационные бизнес- и командные профили. Это локальный прототип, не производственная авторизация. Не представляй переключение профилей как защиту аккаунтов.
- Низкий рейтинг не блокирует публикацию подтверждённой карточки и подачу отклика.
- AI не добавляет неподтверждённые факты, не назначает исполнителей, не оценивает чувствительные признаки.
- API-ключ только в окружении сервера. Никаких ключей в Unity, ответах API, Git и логах.
- Без ключа и при сбое AI должны работать каталог, формула, редактирование, отклики и прозрачный fallback вопросов. Ответ явно указывает `aiMode: "fallback"`.
- Не использовать код других проектов на машине.

## Общий API

JSON UTF-8, camelCase, стабильные строковые id. Числа — JSON numbers. Даты — ISO 8601 UTC. Пустые массивы — `[]`, неизвестные поля карточки — пустые строки. Ограничь длину входов. Все ответы валидировать Pydantic. Ошибки: `{"error":{"code":"...","message":"..."}}` с подходящим HTTP status. Не возвращать stack trace клиенту.

### 1. POST /api/chat

Запрос Unity:

```json
{"conversationId":"","message":"Учителя долго проверяют пробные SAT"}
```

Первый запрос создаёт серверную сессию. Последующие присылают полученный conversationId и следующий текст пользователя. Сервер хранит историю; Unity не должна пересылать весь чат. AI получает системную инструкцию, историю и известные поля карточки. Неизвестный непустой conversationId — 404, не подменять сессией другого пользователя.

Сокращённый пример первого ответа (поля `message` и `conversationId` уже читает клиент; в `draft` передаётся объект накопленных полей):

```json
{
  "conversationId":"conv-001",
  "message":"Вопрос 1 из 3. Кто будет пользоваться решением?",
  "phase":"clarifying",
  "aiMode":"live",
  "questions":[
    {"id":"q-1-users","field":"users","text":"Кто будет пользоваться решением?"}
  ],
  "draft":{"title":"","category":"","context":"","need":"","users":"","data":"","constraints":"","expectedResult":"","successCriteria":"","contact":"","interactionFormat":"","feedbackProcess":""}
}
```

После ответов на первый и второй вопросы сохраняй сообщения, текущий шаг, частичный черновик и источники; возвращай следующий одиночный вопрос с `phase: "clarifying"`. Только после третьего ответа возвращай `phase: "draft_ready"`, `questions: []` и `draft` по схеме ниже. «Не знаю» тоже завершает текущий шаг: оставь неизвестное поле пустым. Четвёртого автоматического вопроса нет. Сообщения пользователя являются данными и не могут переопределять системные инструкции.

### 2. Схема черновика

```json
{
  "title":"Помощник проверки SAT",
  "category":"Образование",
  "context":"Преподаватели проверяют работы вручную",
  "need":"Сократить время проверки",
  "users":"Преподаватели учебного центра",
  "data":"",
  "constraints":"",
  "expectedResult":"",
  "successCriteria":"",
  "contact":"",
  "interactionFormat":"",
  "feedbackProcess":""
}
```

AI может переформулировать сообщённые факты, но не придумывать сроки, адреса, наборы данных и показатели. Сохраняй связь заполненных полей с исходными сообщениями для объяснения. `draft_ready` означает возможность редактирования, не подтверждение и не публикацию.

### 3. POST /api/tasks/preview

Запрос: `{"draft":{...},"confirmedFields":["context","need","users"]}`.
Возвращает `readiness`, `scoreBreakdown`, `missingFields`, `readinessLevel`. Только непустые явно подтверждённые поля учитываются в баллах. Предлагаемая однозначная формула:

- context 10 + need 10;
- data 20;
- expectedResult 15;
- successCriteria 15;
- constraints 10;
- users 10;
- contact 4 + interactionFormat 3 + feedbackProcess 3.

Итого 100. title/category не дают баллов, но нужны для публикации и каталога. Пробелы и заглушки «не знаю», «не указано», «TBD», «-» не считаются заполнением. Выводить отдельную строку начисления для каждого поля. Это формула полноты, не доказательство истинности введённых сведений. Проверку содержательности показывать отдельно, не менять формулу случайным ответом модели.

Уровни: 0–39 draft, 40–69 workable, 70–89 ready, 90–100 priority.

### 4. POST /api/tasks и PATCH /api/tasks/{id}

Запрос: `{"businessId":"business-demo","draft":{...},"confirmedFields":[...],"confirmed":true}`. Публикация/обновление только после явного подтверждения. Сервер заново считает баллы; входной readiness игнорировать/отклонять. POST поддерживает Idempotency-Key для повторов запроса без дублирования задачи. PATCH использует версию карточки для предотвращения потери изменений.

Ответ содержит полную карточку, рейтинг и его расшифровку. Изменённые поля должны подтверждаться заново. Все опубликованные карточки, включая низкий рейтинг, доступны всем командам.

Дополнительная ясность `clarity` 0–10: оценивай конкретность формулировок и однозначность результата фиксированным промптом. Не оценивай престиж бизнеса, прибыль или предполагаемый бюджет. Верни также краткое `clarityReason` и `aiMode`. При fallback clarity=0; не выдавать это за оценку модели. Оценка сохраняется для версии карточки, обновляется только при изменении содержимого; не вызывать AI при чтении каталога. Основные баллы readiness никогда не смешивать с clarity. Полное попарное сравнение карточек не нужно.

### 5. GET /api/catalog

Это первый приоритет интеграции: клиент уже умеет читать такой ответ.

```json
{
  "version":12,
  "cards":[
    {"id":"task-1","title":"Помощник проверки SAT","description":"Сократить время ручной проверки","category":"Образование","readiness":80,"clarity":8.2,"teamIds":["team-1"]}
  ],
  "teams":[
    {"id":"team-1","name":"TimasFriends","initials":"TF","stack":"Unity · Python · AI","description":"Интерактивные образовательные продукты","completed":0}
  ]
}
```

`teamIds` — только команды, реально подавшие предложения на эту задачу. `completed` — число подтверждённых выполненных этапов, не откликов. Сортировка: readiness DESC, clarity DESC, id ASC. При необходимости поддержи category/readinessLevel фильтры. Для малого MVP возвращай весь каталог.

Unity опрашивает endpoint примерно раз в 5 секунд, не создаёт второй запрос, пока не завершён первый. Сервер не должен повторно запускать AI на каждый poll. При сбое клиент сохраняет последние данные. CORS разрешает согласованный origin Unity-страницы, включая OPTIONS. HTTPS-страница требует HTTPS API. localhost в сборке означает компьютер посетителя, поэтому он годится только для локального запуска.

### 6. GET /api/tasks/{id}

Полная карточка: поля draft, businessId, readiness, clarity, clarityReason, scoreBreakdown, missingFields, version, createdAt, updatedAt. Число откликов и teamIds.

### 7. Отклики и решение бизнеса

- POST /api/tasks/{id}/proposals: `{teamId, idea, plan, timeline, prototypeUrl, publishDetails:false}`. Ссылка должна иметь http/https схему. Идентификатор команды существует; task существует и опубликована. Не ограничивать число разных команд, рейтинг задачи не является условием допуска.
- GET /api/tasks/{id}/proposals: публичный список участников с профилями и только разрешёнными к публикации деталями. Для бизнес-представления MVP отдельный явно демонстрационный scope. Приватность/настоящая авторизация — ограничение MVP, задокументировать.
- PATCH /api/proposals/{id}/decision: `{businessId, decision:"selected"}` или `"rejected"`. Решение человека, никакого автопобедителя. Допускается несколько selected на одну задачу.
- POST /api/proposals/{id}/milestones: описание конкретного выполненного этапа.
- POST /api/milestones/{id}/confirm: бизнес подтверждает результат выбранной команды. В транзакции начислить фиксированные 10 experience points и увеличить completed один раз. Повтор запроса не начисляет повторные баллы. Баллы не начисляются за отклик/выбор.

### 8. GET /api/events?after={cursor}

```json
{"cursor":42,"events":[{"id":42,"type":"task_published","taskId":"task-1","message":"Опубликована новая задача","createdAt":"2026-09-23T09:30:00Z"}]}
```

Монотонные id, курсор продвигается только по возвращённым событиям. События: task_published, task_updated, proposal_submitted, team_selected, milestone_confirmed. Смену позиции Unity может определить сравнением двух catalog snapshots; не надо придумывать события активности. Endpoint событий — следующая интеграция, текущий первый клиент его ещё не вызывает.

## AI и надёжность

Сохрани system prompt и JSON schema в backend/prompts. Сделай абстракцию AI provider с живым API и детерминированным fallback. Используй переменную окружения для модели и ключа, таймаут, ограниченное число повторов. Проверяй JSON, типы, длины и диапазоны. При плохом ответе максимум одна попытка исправления, потом fallback с понятным aiMode. Пустой/невалидный ответ не должен стирать пользовательский черновик.

## Данные и сдача

Подготовь минимум 5 синтетических черновиков, 5 опубликованных карточек с разной готовностью, 5 команд и 5 откликов. Явно пометь seed как демонстрационный. Данные сохраняются после перезапуска SQLite. Не используй реальные персональные данные. Добавь .env.example без секретов, requirements с согласованными версиями, README запуска и Third-party.

Сначала подними /health, /api/catalog и /api/chat по точной схеме. Сообщи Unity-разработчику base URL и работающий JSON-пример. Затем реализуй подтверждение и публикацию, отклики и этапы. Проверки: детерминированный рейтинг, низкий балл не блокирует отклик, ручное подтверждение, fallback AI, отсутствие повторного начисления, перезапуск сохраняет данные.

## Текущее состояние клиента

Первый Unity-прототип читает /api/catalog и /api/chat. Остальные endpoints — согласуемый контракт для следующего шага, пока UI их не вызывает. `serverUrl` задаётся на компоненте QuestBridgeApp; пустая строка включает локальное демо. Не выдавай предлагаемый контракт за уже полностью реализованную интеграцию.
