# QuestBridge — сервер демонстрационного MVP

Для жюри: [пошаговый запуск проекта](../README.md#запуск-для-жюри) — подготовка Python, окружения и `.env`, запуск backend, проверка соединения и открытие Unity/WebGL.

FastAPI + Pydantic + SQLite для клиента Unity **6000.3.7f1 / WebGL**. Сервер принимает описание проблемы, помогает собрать черновик, считает готовность и сохраняет подтверждённые задачи, отклики и этапы. Без API-ключа весь сценарий работает с детерминированным помощником и `aiMode: "fallback"`.

Клиент Unity подключает каталог, чат, предпросмотр рейтинга, публикацию и редактирование задач, отклики, ручной выбор команд и этапы. Каталог и списки откликов/этапов обновляются примерно каждые пять секунд; API событий доступен отдельно. Схема, настройки сцены и запуск клиента приведены в [корневом README](../README.md), подробный контракт — в [docs/API.md](../docs/API.md).

## Запуск без ключей

Нужен Python 3.12. Все команды ниже выполняются **из корня репозитория**. Для первой установки пакетов нужен доступ к индексу Python; после установки режим fallback не обращается к AI API.

Windows / PowerShell:

```powershell
py -3.12 -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
backend/.venv/Scripts/python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Linux / macOS, где `python3` — Python 3.12:

```bash
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
backend/.venv/bin/python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Base URL: **`http://127.0.0.1:8000`**. В отдельном PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8000/api/catalog
```

Без ключа и модели `/health` возвращает:

```json
{"status":"ok","service":"questbridge","aiMode":"fallback","demo":true}
```

Описание всех схем: [OpenAPI JSON](http://127.0.0.1:8000/openapi.json). Интерактивные запросы: [Swagger UI](http://127.0.0.1:8000/docs). Swagger UI использует внешние ресурсы браузера; сами JSON endpoints работают без них.

Чтобы использовать файл настроек, один раз скопируйте пример, измените необходимые значения и перезапустите сервер с `--env-file`:

```powershell
Copy-Item backend/.env.example backend/.env
backend/.venv/Scripts/python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --env-file backend/.env
```

В Linux эквивалент копирования: `cp backend/.env.example backend/.env`. Не заменяйте уже настроенный `.env` повторным копированием. Обычный запуск без `--env-file` читает переменные окружения процесса. Значения `OPENAI_API_KEY` и `AI_MODEL` по умолчанию пустые.

## Подключение Unity и CORS

На компоненте `QuestBridgeApp` установите **Server Url = `http://127.0.0.1:8000`**. Пустое значение включает локальное демо клиента. Запустите сервер, затем сцену проекта по инструкции в корневом README; проверьте каталог и ответ чата. Клиенту достаточно отправлять очередной текст и полученный `conversationId`, история хранится сервером.

В `CORS_ORIGINS` перечисляются точные origins страницы WebGL через запятую. По умолчанию разрешены `http://localhost:8080` и `http://127.0.0.1:8080`. Origin включает протокол, имя хоста и порт; другой порт нужно добавить отдельно. Сервер разрешает `GET`, `POST`, `PATCH`, `OPTIONS`, заголовки `Content-Type` и `Idempotency-Key`. См. [документацию FastAPI о CORS](https://fastapi.tiangolo.com/tutorial/cors/).

Для HTTPS-страницы WebGL нужен HTTPS API, иначе браузер блокирует mixed content. В опубликованной сборке `localhost` и `127.0.0.1` означают компьютер посетителя. Для общего показа укажите доступный адрес сервера и соответствующий origin; HTTPS обычно обеспечивает прокси перед Uvicorn. CORS регулирует доступ браузера и не заменяет авторизацию.

Каталог можно опрашивать примерно раз в 5 секунд, дожидаясь окончания предыдущего запроса. При сетевой ошибке клиент сохраняет последний снимок. Чтение каталога не вызывает AI. Его `version` помогает заметить изменения, а перемещение карточек определяется сравнением снимков.

## Данные и демонстрационные профили

При первом запуске создаются пять синтетических черновиков, пять опубликованных задач с разной готовностью, пять команд и пять откликов. Seed содержит явные демонстрационные подписи; опубликованные seed-карточки имеют `demo: true`. Это вымышленные сведения без реальных персональных данных.

| Идентификаторы | Назначение |
| --- | --- |
| `business-demo` | Демонстрационный владелец seed-задач; используется в примерах |
| `business-school` | Второй демонстрационный бизнес для проверки принадлежности |
| `team-1` … `team-5` | Пять доступных команд |
| `conv-demo-1` … `conv-demo-5` | Сохранённые демонстрационные черновики чата |

Повторная инициализация использует отметку seed в SQLite и не дублирует исходные задачи. `SEED_DEMO=false` отключает добавление синтетических задач и чатов в новой базе, сохраняя демонстрационные бизнес- и командные профили. Эта настройка не удаляет уже сохранённые записи.

Набор воспроизводимых черновиков: [examples/demo_drafts.json](examples/demo_drafts.json), форма `{"demo":true,"drafts":[...]}`. Выполняемый пример [examples/demo.py](examples/demo.py) читает этот файл, проходит сценарий публикации, отклика, выбора и подтверждения этапа и выводит результат. Он создаёт записи в запущенном сервере:

```powershell
backend/.venv/Scripts/python.exe backend/examples/demo.py
```

## Черновик, вопросы и подтверждение

Черновик содержит 12 строк: `title`, `category`, `context`, `need`, `users`, `data`, `constraints`, `expectedResult`, `successCriteria`, `contact`, `interactionFormat`, `feedbackProcess`. Неизвестные значения представлены пустой строкой, пустые коллекции — `[]`.

Первый запрос чата с `conversationId: ""` создаёт сессию. Помощник задаёт **три вопроса по очереди**: исходное описание → вопрос 1 → ответ → вопрос 2 → ответ → вопрос 3 → ответ → редактируемый черновик. До третьего ответа `phase: "clarifying"`, в `questions` ровно один текущий вопрос; после третьего — `phase: "draft_ready"` и `questions: []`. Непустой неизвестный `conversationId` возвращает 404.

Каждое сообщение пользователя, ответ помощника, текущий вопрос, частичный черновик и источники сохраняются в одной транзакции SQLite. После перезапуска сервер продолжает тот же разговор по `conversationId`. В fallback обычный ответ записывается в поле текущего вопроса; явные строки `пользователи: …`, `данные: …` тоже поддерживаются. «Не знаю» засчитывается как ответ и переводит к следующему вопросу, оставляя неизвестное поле пустым. Четвёртый вопрос автоматически не задаётся.

`phase: "draft_ready"` означает готовность к редактированию. Публикация требует отдельного человеческого `confirmed: true`; строка `"true"` не принимается. Для каждого начисляемого поля человек отдельно указывает имя в `confirmedFields`. Низкая готовность допускает публикацию и отклики. Для публикации обязательны содержательные `title` и `category`.

В режиме `clarifying` возвращается частично заполненный `draft`. Известные поля сохраняются после каждого ответа, включая переход с живого AI на fallback.

В `sources` сохраняются связи `{field, messageId, quote}` с пользовательскими сообщениями. Передайте `conversationId` при публикации, чтобы перенести доступные источники. После ручного изменения текста несоответствующая цитата удаляется. В текущем MVP заполнение AI принимается только при проверяемой связи текста с цитатой пользователя; неизвестный или невалидный ответ не стирает известный черновик. Саму публикацию, выбор команд и подтверждение этапа AI не выполняет.

### Проверка содержания

Чат проверяет исходное описание и каждый следующий ответ. При бессвязном тексте, инструкции обойти правила или ответе не по теме поля возвращается `inputAccepted: false`, объяснение в `message` и `validation.issues`. Ранее принятый черновик сохраняется, текущий вопрос повторяется. Отклонённое сообщение остаётся в истории с соответствующей отметкой, но не участвует в извлечении фактов и не расходует один из трёх шагов. «Не знаю» допустимо как ответ на уточнение; вместо начального описания проблемы помощник попросит написать саму проблему.

`POST /api/tasks/preview` проверяет смысл заполненных полей до расчёта готовности. Ответ чата, предпросмотра и сохранённая карточка содержат `validation`:

```json
{
  "status": "rejected",
  "aiMode": "fallback",
  "issues": [{"field": "context", "code": "gibberish", "message": "Контекст: смысл текста неясен. Опишите текущую ситуацию обычными словами."}],
  "message": "Исправьте отмеченные поля."
}
```

Статусы: `passed` — проверка пройдена; `rejected` — есть ошибки; `unavailable` — настроенный AI временно не смог выполнить проверку. `aiMode` внутри `validation` показывает источник именно этой проверки. Живой AI оценивает осмысленность, соответствие полю и согласованность текста; он не устанавливает истинность заявленных фактов и не добавляет сведения за пользователя. Исправления остаются за человеком.

Локальная проверка отсекает явные клавиатурные наборы, повторы и одинаковые заглушки в разных полях. Без AI-ключа она позволяет пройти демонстрационный сценарий и явно обозначается как локальная. Она не распознаёт любой бессмысленный текст. При ошибке настроенного AI предпросмотр возвращает `unavailable` и не начисляет баллы до успешного повтора; публикация и изменение карточки возвращают 503 `content_review_unavailable`. Результат сбоя не кэшируется.

Неверное поле не получает баллы, даже если его подтвердили. Если отклонены название или категория, рейтинг всей карточки остаётся нулевым до исправления. Публикация и редактирование дополнительно проверяются на сервере: при ошибках возвращается 422 `content_invalid` с подсказкой, записи и события не создаются. Пустые неизвестные поля допускаются с нулевым вкладом; низкая готовность сама по себе не запрещает публикацию.

В Unity проверка запускается после паузы в наборе; ошибки показываются у полей. Пока идёт проверка или исправления не приняты, подтверждение и публикация недоступны. Для одинакового содержания сервер переиспользует проверку до 60 секунд; кэш ограничен 128 результатами. Чтение каталога и опрос событий AI не вызывают. Уже сохранённые карточки автоматически не перепроверяются; новая проверка выполняется при предпросмотре и сохранении изменений.

### Обновление и защита от повторов

`POST /api/tasks` поддерживает `Idempotency-Key`: один ключ для одного намерения публикации. Повтор с тем же нормализованным запросом возвращает исходный сохранённый ответ без новой задачи, даже если задачу уже отредактировали. Актуальное состояние получите через `GET /api/tasks/{id}`. Другой запрос с уже использованным ключом возвращает 409; область ключа — `businessId`.

`PATCH /api/tasks/{id}` принимает `businessId`, **весь новый `draft`**, полный список `confirmedFields`, `confirmed: true`, текущую целочисленную `version` и `reconfirmedFields`. Это замена черновика: пропущенные поля становятся пустыми строками. Получите актуальную карточку перед редактированием; чужая версия возвращает 409.

Изменённое поле может остаться в `confirmedFields` только после нового явного подтверждения, указанного в `reconfirmedFields`. Например, после изменения `need` добавьте его в `reconfirmedFields` при повторном согласии человека либо уберите из `confirmedFields`, чтобы оно перестало приносить баллы. Простое перенесение старых отмеченных флажков приводит к 409 `reconfirmation_required`. Неизменённые подтверждённые поля не требуют повторной отметки.

## Рейтинг

`POST /api/tasks/preview` принимает `{draft, confirmedFields}`. Сервер одинаково пересчитывает формулу при предпросмотре, публикации и изменении задачи; входной `readiness` отклоняется как лишнее поле.

| Поле | Баллы |
| --- | ---: |
| `context` | 10 |
| `need` | 10 |
| `data` | 20 |
| `expectedResult` | 15 |
| `successCriteria` | 15 |
| `constraints` | 10 |
| `users` | 10 |
| `contact` | 4 |
| `interactionFormat` | 3 |
| `feedbackProcess` | 3 |
| **Итого** | **100** |

`title` и `category` баллов не дают. Поле получает свой полный вес только при содержательном непустом значении, присутствии в `confirmedFields` и отсутствии ошибки проверки этого поля. Веса остаются фиксированными; AI может отклонить содержание, но не назначает числовой рейтинг. Пробелы, знаки пунктуации и заглушки вроде «не знаю», «білмеймін», «не указано», `TBD`, `N/A`, `-` не считаются заполнением. Повтор имени в списке подтверждений не увеличивает результат.

`scoreBreakdown` содержит десять строк `{field, maxPoints, points, filled, confirmed}`. `missingFields` в рейтинге перечисляет все поля без начисленных баллов, включая заполненные, но неподтверждённые. В ответе чата `missingFields` обозначает неизвестные поля черновика, включая название и категорию.

Уровни: 0–39 `draft`, 40–69 `workable`, 70–89 `ready`, 90–100 `priority`. Это проверяемая формула полноты: она не доказывает истинность или качество введённых фактов.

Дополнительная `clarity` от 0 до 10 оценивает конкретность и однозначность формулировки. AI не учитывает престиж бизнеса, прибыль, бюджет или чувствительные признаки. `clarityReason` объясняет результат. При fallback `clarity=0` обозначает отсутствие оценки модели. Оценка сохраняется с карточкой и повторяется только при изменении её содержимого; изменение одних подтверждений или чтение каталога её не запускают.

Каталог отсортирован по `readiness DESC`, затем `clarity DESC`, затем `id ASC`. Две оценки не складываются. Каждая карточка содержит `businessId` владельца для вкладки «Мои задачи». `teamIds` содержат только команды с реальными откликами на задачу. `completed` — количество подтверждённых этапов.

## API

JSON UTF-8, имена полей camelCase, числа — JSON numbers, даты — ISO 8601 UTC. Схемы запросов и ответов валидирует Pydantic, неизвестные поля отклоняются. В path ниже `{id}` обозначает идентификатор соответствующего объекта.

| Метод и путь | Запрос / назначение |
| --- | --- |
| `GET /health` | Доступность хранилища, сервис и настроенный режим AI |
| `GET /api/catalog` | `{version,cards,teams}`; фильтры `category`, `readinessLevel` |
| `POST /api/chat` | `{conversationId:"",message}`; продолжение по полученному id |
| `POST /api/tasks/preview` | `{draft,confirmedFields}` → баллы и расшифровка |
| `POST /api/tasks` | `{businessId,draft,confirmedFields,confirmed,conversationId?}`; заголовок `Idempotency-Key` необязателен |
| `GET /api/tasks/{id}` | Полная карточка, версия, источники, рейтинг, команды, число откликов |
| `PATCH /api/tasks/{id}` | Полный запрос публикации + `version`, `reconfirmedFields` |
| `POST /api/tasks/{id}/proposals` | `{teamId,idea,plan,timeline,prototypeUrl,publishDetails:false}` |
| `GET /api/tasks/{id}/proposals` | `{proposals:[...]}`; публичный список, `scope=demo-business&businessId=business-demo` либо `scope=demo-team&teamId=team-1` |
| `PATCH /api/proposals/{id}/decision` | `{businessId,decision:"selected"}` либо `"rejected"` |
| `POST /api/proposals/{id}/milestones` | `{teamId,description}` от выбранной команды |
| `GET /api/proposals/{id}/milestones` | `{milestones:[...]}`; `scope=demo-business&businessId=business-demo` либо `scope=demo-team&teamId=team-1` |
| `POST /api/milestones/{id}/confirm` | `{businessId}` → этап и обновлённый профиль команды |
| `GET /api/events?after=0&limit=100` | `{cursor,events}`; `after>=0`, `limit` от 1 до 200 |

На одну задачу допускается один отклик каждой команды; повтор возвращает 409. Разных команд может быть несколько, рейтинг не ограничивает участие. `prototypeUrl` обязателен и должен быть абсолютным HTTP(S) URL. `idea`, `plan` и `timeline` должны быть непустыми.

Бизнес вручную выбирает одну, несколько или ни одной команды. Отклик или выбор не дают опыта. Только подтверждение конкретного этапа выбранной команды атомарно добавляет **10 experience** и **1 completed**. Повтор подтверждения того же этапа возвращает сохранённый результат без повторного начисления.

События имеют монотонные id и типы `task_published`, `task_updated`, `proposal_submitted`, `team_selected`, `milestone_confirmed`. Сохраняйте возвращённый `cursor` и передавайте его в `after`. Курсор продвигается только по выданным событиям, при пустом ответе остаётся равным `after`. Endpoint событий пока не используется первым клиентом Unity.

### Демонстрационные права и видимость откликов

При `scope=public` (по умолчанию) участники и профили видны всем, а `details` равен `null`, если автор не установил `publishDetails: true`. Создатель отклика получает свои детали в ответе POST. Представление `scope=demo-business&businessId=...` показывает детали владельцу задачи; запрос решения бизнеса также возвращает их. Представление `scope=demo-team&teamId=...` позволяет команде после перезапуска загрузить собственный полный отклик; чужие отклики сохраняют публичные правила видимости. Для него обязателен существующий `teamId`.

Список этапов доступен только демонстрационному бизнесу — владельцу задачи либо команде — автору соответствующего отклика. Для `GET /api/proposals/{id}/milestones` нет публичного режима: по умолчанию используется `scope=demo-business`, которому нужен `businessId`. Команда явно передаёт `scope=demo-team&teamId=...`. Возвращается `{"milestones":[]}`, если этапов ещё нет, иначе полные объекты этапов в порядке `createdAt`, затем `id`. Подтверждённые этапы также остаются в списке. Отсутствующий id профиля возвращает 422 `business_required`/`team_required`, неизвестный — 404, чужой существующий владелец — 403 `business_mismatch`/`team_mismatch`.

`businessId` и `teamId` — переключатели демонстрационных профилей. Проверяется существование профиля и принадлежность задачи/отклика, но у MVP нет регистрации, входа или доказательства личности. Любой клиент, знающий id владельца, может запросить демонстрационное бизнес-представление. Этот scope не обеспечивает настоящую конфиденциальность; используйте синтетические данные.

### Ограничения и ошибки

Максимальный размер тела запроса — **64 KiB**. Сообщение чата — до **6000 символов**, одна сессия — до **50 пользовательских сообщений**. После лимита создайте новую сессию; прежние данные сохраняются. Поля черновика — до **2000 символов**, `title` — до **160**, `category` — до **100**. Идея, план, срок и описание этапа — до **2000** каждый. Идентификаторы — до **80** символов из букв латиницы, цифр, `_` и `-`. Входные строки обрезаются по краям, а чрезмерная длина отклоняется.

Ошибки имеют единую форму без stack trace:

```json
{"error":{"code":"version_conflict","message":"Карточка уже изменена. Загрузите её актуальную версию."}}
```

Основные статусы: 422 — неверные поля/типы/длины или отклонённое содержание, 404 — неизвестный id, 403 — другой демонстрационный владелец, 409 — конфликт версии/подтверждения/повтора, 413 — слишком большое тело, 503 — временная недоступность SQLite или проверки содержания AI.

## Включение AI

Живой провайдер включается только при одновременном задании `OPENAI_API_KEY` и `AI_MODEL` в окружении сервера либо `backend/.env`. Выберите доступную вашему аккаунту модель с поддержкой Responses API и Structured Outputs. В `.env.example` намеренно нет ключа и выбранной модели; ключ не передаётся Unity и не должен попадать в Git или логи.

Провайдер отправляет запросы через `httpx` в Responses API с JSON schema в `text.format`, `strict: true` и `store: false`. Формат API описан в [официальной документации OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Фиксированные системные инструкции и схемы находятся в [prompts/](prompts/). Пользовательские сообщения передаются как данные; они не получают полномочий системной инструкции.

Необязательный `AI_REASONING_EFFORT` передаётся как `reasoning.effort` только при непустом значении. Для `gpt-6-luna` можно задать `AI_REASONING_EFFORT=none`, чтобы снизить задержку извлечения черновика; модель по умолчанию использует `medium` ([официальная документация модели](https://developers.openai.com/api/docs/models/gpt-6-luna)). Для другой модели проверьте поддержку выбранного значения; пустая настройка оставляет поведение провайдера по умолчанию.

По умолчанию каждая попытка ограничена **10 секундами**, всего допускается **две попытки**, включая максимум одно исправление невалидного ответа. `AI_TIMEOUT_SECONDS` позволяет сократить ожидание; рабочий сервис ограничивает значение сверху десятью секундами. Общее ожидание AI ограничено 20 секундами и укладывается в 25-секундный таймаут чата Unity. При сетевой ошибке, отказе, неверном JSON, типах, диапазонах или непроверяемом источнике включается fallback. Некоторые постоянные ошибки API сразу приводят к fallback. `aiMode` в ответе чата/карточке отражает фактически использованный режим; режим `/health` показывает наличие конфигурации, а не успешность внешнего вызова.

Fallback задаёт вопросы по отсутствующим полям, извлекает явно указанные пользователем сведения и объясняет пробелы. Без ключа весь сценарий доступен с локальной проверкой. Если ключ настроен, но смысловая проверка AI завершилась ошибкой, сохранение карточки ждёт успешного повтора; каталог, отклики и этапы остаются доступны. Проверка наличия источника ограничивает добавление фактов, но не устанавливает истинность слов пользователя: карточку проверяет человек.

## Хранение и перезапуск

SQLite по умолчанию находится в `backend/data/questbridge.sqlite3`; данные сохраняются после перезапуска. `QUESTBRIDGE_DB` задаёт другой путь; относительный путь считается от каталога запуска. Папка данных, `.venv`, `.env` и временные файлы исключены из Git.

Для простой резервной копии остановите все процессы сервера, дождитесь завершения, затем скопируйте файл SQLite в отдельное место. Если рядом остались файлы `-wal`/`-shm`, сохраняйте их вместе с базой. Не копируйте только основной файл активно изменяемой базы: незавершённый WAL может содержать нужные данные. Для нового чистого демо проще задать отдельный `QUESTBRIDGE_DB`, сохранив старую базу.

## Проверки

Установите зависимости разработки и запустите набор тестов из корня репозитория:

```powershell
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements-dev.txt
backend/.venv/Scripts/python.exe -m pytest backend/tests -q
```

На Linux замените путь интерпретатора на `backend/.venv/bin/python`. Тесты используют временные базы и подменённый AI transport; реальный ключ не нужен. Покрываются формула и границы уровней, строгие типы, подтверждения, fallback, публикация с низким баллом, отклики, владение демо-профилями, повторное начисление, события и сохранение данных при перезапуске. Итог конкретного запуска смотрите в выводе pytest.

### Прогон с настоящим AI

После настройки ключа и модели в `backend/.env` выполните:

```powershell
backend/.venv/Scripts/python.exe -m backend.examples.live_smoke
```

Скрипт отправляет настоящие платные запросы провайдеру на вымышленных данных учебного центра «Орбита». Он проверяет три последовательных уточнения с отдельными ответами, извлечение черновика и источников, неизвестные поля, готовность 0 → 90 после подтверждения, AI-оценку ясности, публикацию, два отклика, выбор команд, однократное начисление опыта и сохранение после перезапуска приложения. Если любой AI-этап использует fallback, прогон завершается с ошибкой.

Для каждого запуска создаются отдельная SQLite-база и подробный `report.json` в `backend/data/live-smoke-<дата>-<id>/`. Основной каталог не изменяется. Запросы к FastAPI выполняются через TestClient, запросы к AI — по настоящей сети. Unity, браузер и сетевой запуск Uvicorn этот скрипт не проверяет. Зависимости из `requirements-dev.txt` обязательны.
